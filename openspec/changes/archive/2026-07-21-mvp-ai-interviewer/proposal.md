# MVP: AI 面试官 (简历 + JD + 6 档分级)

## Why

求职者练面试需要一个**贴合个人背景、目标岗位、职级**的模拟工具,而不是通用题库的问答。当前市场多数 AI 面试产品要么只做通用面、不针对简历 / JD 定制,要么要做到这个粒度成本极高。MVP 阶段用最简实现验证"求职者愿不愿意在流式对话里对着 AI 答完一场面试 + 拿到报告"这个核心需求,暂不解决打分可信度等深水区。

## What

一个 Streamlit 单页应用,完成"上传简历 → 配置 → 一问一答 → 报告"完整闭环。

### 核心输入(侧边栏)
- **简历上传**:PDF 格式(只做文本抽取,不结构化)
- **JD 粘贴**:纯文本(text_area)
- **面试等级**:6 档(校招 / 实习 / 社招初级 / 社招中级 / 社招高级 / 社招资深)
- **面试风格**:温和引导 / 压力深挖(2 选 1)

### 核心流程
1. 用户点击"开始面试" → 调一次 LLM 生成开场问题
2. 用户在 `st.chat_input` 输入回答 → 调 LLM 生成下一题(系统 prompt 始终在前,带等级 / 风格 / 简历 / JD)
3. 循环,直到用户说"结束面试"或点击结束按钮
4. 调一次 LLM 生成六维评估报告

### 报告口径:**教练复盘**,不写"录用建议"
报告主体是**给求职者的改进建议**,而非招聘官的录用判定。系统 prompt 改为"面试教练"人设,六维打分保留但解读口径改向"成长性"。

> 决策:这是从"模拟评委"切换到"辅导教练"的最小成本改动,只动 prompt 一行,不加工作量。如果市场验证阶段用户明确要"录用建议"再加回来。

## Non-Goals(MVP 明确推后)

| 类别 | 推后内容 | 为什么不是 MVP |
|---|---|---|
| 简历处理 | Word 解析 / 结构化抽取(技术栈 / 项目年限) | 多数简历 PDF 可用,结构化抽取需要模型容错设计 |
| 多模态 | 语音作答 / TTS 读题 / 英文模式 | 引入 ASR/TTS 后端 + 成本 + 延迟三重负担 |
| 评估可信度 | 六维打分校准 / 防虚高 / 每轮即时评分 | LLM 单次自评必然虚高聚拢,需要专门设计 |
| 分级硬约束 | 越级提问防护 / 真实度矛盾检测 | 纯 prompt 不可靠,需要硬机制兜底 |
| 持久化 | 历史记录 / 跨会话 / 报告导出 PDF | Streamlit session_state 重启即失,MVP 暂接受 |
| 鉴权 | 用户登录 / 多用户隔离 | 单机本地工具,MVP 不需要 |

## Out of Scope 之外仍然成立的设计目标

即便 MVP 只做最简实现,以下三条**不让步**:

1. **一问一答循环不能机械** — AI 必须顺着候选人上一条回答追问,不能按固定题库自顾自问
2. **6 档分级要肉眼可感** — 校招生不该被问架构,8 年经验的不能只聊基础
3. **报告要给出可执行的下一步** — 不能是"基础扎实、综合表现良好"这种正确但没用的套话

## Deliverables

- `app.py` — Streamlit 单页应用主入口
- `prompts.py` — 面试官系统 prompt + 报告 prompt(常量 + 拼接函数)
- `resume_parser.py` — PDF 文本抽取(只支持 PDF,Word 推后)
- `config.py` — 从环境变量读 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`,默认指向 MiniMax-M3
- `requirements.txt` — streamlit / openai / pypdf2
- `tests/` — 单元测试(prompt 拼接 / PDF 解析 / 配置读取)+ 真实 LLM smoke test(stub 启动,需手动跑)
- `README.md` — 启动命令、配置项、demo 流程

## Validation

- 单元测试:prompt 拼接在 6 档 × 2 风格 = 12 组合下行为可预测;PDF 解析对 fixture 文件能稳定抽到关键字段
- 真实 LLM smoke(手动跑):上传一份 PDF + 一段 JD,选"社招中级 + 压力",答满 5 轮,生成报告。验收:问题有针对性追问,报告六维各有打分依据且不全是 7-8
